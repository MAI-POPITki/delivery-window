# Расширение применения: ZXC

Приоритет: (1) другие регионы, (2) речной завоз, (3) удалённые объекты.

## Что реализовано

Вкладка «Расширение применения» использует единый двухступенчатый расчёт.
Доступны пять существующих регионов; показаны записи регионального реестра
с датами и URL для выбора конкретного пилота. Новые территории без данных
не объявляются подтверждёнными. Экономика по регионам автоматически не переносится.

Полиморфизм: `Availability.calendar(horizon)` задаёт общий интерфейс календаря.
`Closure` закрывает основной канал на период; `SeasonalWindow` открывает его
только внутри периода; `ServiceDays` задаёт отдельные дни обслуживания.
Существующий экономический решатель принимает календарь без смены модели льда.
Прежний коридор работает как раньше, если календарь не передан.

Соперники получают одинаковые потребность, мощности, цены и календарь:
пополнение по остатку (существующая эвристика без сезонного предзавоза) и LP.
Соперник — модельное правило, не установленная практика перевозчика.
Выводятся расходы периода, конечная оценка довоза, обслуживание, очередь,
ожидание и баланс массы. Дневной CSV содержит регион, маршрут и отметку,
что календарь предполагался известным заранее.

## Границы результата

Все вводимые даты, объёмы и цены — сценарные допущения. Нет нового обучения ML,
доказанной переносимости прогнозов, реальных рейсов или обещания экономии.
Заданный календарь известен целиком на старте. Это детерминированный сценарий,
не ретроспективный прогноз с доступной в тот момент информацией.
При изменении окна сценарий нужно рассчитать заново; ошибки прогноза не моделируются.

Модель: база → первый транспортный участок с лагом → промежуточный склад →
сезонная доставка в тот же день → склад получателя. Резерв работает только вне
основного календаря. Доставка измеряется делимыми тоннами, без целых машин,
судов, оборота рейсов, правовых ограничений нагрузки и времени второго участка.
Нет ёмкости промежуточного склада. Эти ограничения особенно важны для речных рейсов.
Остатки после горизонта оцениваются прежним методом коридора: обычные тарифы
будущего довоза, без последующего хранения и ожидания. Это не выполненная доставка.

## Как довести до проверяемого примера А3

1. Другой регион: выбрать одну дорогу и получателя из реестра, проверить URL,
   ограничения массы и опубликованный график. Получить план-факт и тарифы оператора.
   Сопоставить график, историческое правило и ML по данным, доступным на дату решения.
2. Речной завоз: выбрать конкретные порты/поселение и груз; получить расписание,
   навигационные ограничения, осадку, вместимость и оборот судов, время всех участков.
   Не приравнивать спутниковое вскрытие к открытию навигации.
3. Удалённый объект: определить базу, объект, ежедневную потребность, дни обслуживания,
   запасы, возможности и время резерва. Проверить выполнимость полного пути.

Для каждого пилота нужны подтверждённая проблема, адресат предложения,
исходный способ работы, конкретное изменение, сопоставимые условия «до/после»,
исходные данные, допущения и ограничения. Расширение метода не заменяет основной
российский транспортный пример А3.

## Проверки

`python scripts/verify_expansion.py`

Семь модельных сценариев / 14 прогонов создают `reports/expansion/verification.md`,
`summary.csv`, дневные CSV и `manifest.json`. В манифесте полностью заданы входы;
сводка содержит SHA-256 каждого дневного файла. Пять региональных случаев намеренно
имеют одинаковые параметры: это проверка независимости расчёта от имени региона,
а не пять доказательств местной экономии. Окна и тарифы не калибруются.

Свой календарь можно загрузить в интерфейсе как CSV с колонками `day,available`:
каждый день от 0 до H−1 ровно один раз, доступность строго 0/1. Пропуски,
дубли и недопустимые значения отклоняются. Календарь явно считается известным
заранее; исторические факты нельзя выдавать за выпущенный тогда прогноз.

`python -m unittest discover -s tests -p test_supply_scenarios.py -v`

Проверяются границы трёх календарей, отсутствие доставки вне окна, лаг первого
участка, склад, баланс массы, сохранение невыполненных заказов, согласованность
с прежним коридором. Старые тесты оптимизатора также должны проходить.
Независимый полный перебор маленькой задачи проверяет оптимум для всех восьми
трёхдневных календарей, включая полностью закрытый путь и повторные открытия.

## Найденные данные для примеров

Реестр `data/external/expansion_cases.json` содержит маршруты, даты, ссылки,
тип источника, ограничения и недостающие параметры. Для навигации через Обь
использован вторичный справочник gp-yamal.ru (сезон 2025); дата конца
не подтверждает точное время остановки. Тариф 1250 ₽ относится к автомобилю
общей массой свыше 7 до 20 т. Пересчёт в ₽/т использует введённую полезную
загрузку и проверяет суммарную массу; это производная оценка, не грузовой тариф.
Для Красноселькупа публикация от 30.04.2026 подтверждает объявление закрытия
с 01.05.2026 и временные ограничения, но не непрерывность работы всего апреля.
Исторические границы не объявляются заранее известным прогнозом.

Экономика остаётся частично условной: открытые публикации не дают спроса,
запасов, фактических отправок и выделенной оператору мощности.
Ни пассажирские тарифы, ни тариф багажа не используются как цена грузового резерва.

## Подключение существующего М1 к речной доставке

В новой вкладке раскрывается раздел «Речной завоз на Лене». Он вызывает
существующий `forecast(..., kind="close")` для спутникового вскрытия у Якутска.
Название close относится к закрытию ледового пути: для речного сценария это
физическая предпосылка весеннего начала перевозок, а не осеннее закрытие реки.
Календарь и квантили М1 преобразуются одинаково: дата + явно заданный сдвиг.
Конец 1 октября условный; прогноз морского льда и осеннего закрытия не реализован.
Параметры экономики общие для всех четырёх прогонов и остаются допущениями.

Это сравнение планов при разных предполагаемых окнах. Исполнение каждого
плана моделируется в его собственном окне: вывод о превосходстве ML над календарём
из такой таблицы делать нельзя. Для этого требуется общий фактический сезон.
М2 показывает только последнюю запись не позднее даты решения, без автоматической
подмены ею навигационного разрешения. Модельная вероятность М2 не откалибрована
как вероятность безопасного прохода судна.

Карта речного сценария выключена по умолчанию и показывает одну точку прогноза.
Непроверенная геометрия судового хода не рисуется. На общей карте слои М2 и
притоков теперь также выключены по умолчанию; пользователь включает их отдельно.

Проверки: `python -m unittest discover -s tests -p test_navigation.py -v`.
Проверяются общий сдвиг и конец сезона, совпадение планов при одинаковых датах,
баланс массы и исключение спутниковых наблюдений из будущего.
