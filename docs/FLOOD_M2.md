# М2 паводков: что видно со спутника

Обновление: [общий результат М1/М2/М3](FLOOD_JOINT_RESULT.md) и
[независимая ручная проверка выделения воды](../reports/flood_m2_benchmark.md).
Новые сцены отбираются по локальной видимости SCL, а не облачности целого тайла.

В дашборде: **Паводки → М2 · вода со спутника**. Прямая ссылка на локальном
сервере: `?module=flood_m2`. М2 отделён от М1: это наблюдение, не прогноз уровня.

М2 читает реальные снимки **Copernicus Sentinel-2 L2A** через публичный
[Microsoft Planetary Computer](https://planetarycomputer.microsoft.com/dataset/sentinel-2-l2a).
Для каждого из пяти гидропостов берётся квадрат 12×12 км, каналы приводятся
к одной сетке UTM с пикселем 20 м. Курган тоже включён: для спутникового
наблюдения многолетний ряд уровней не нужен.

## Что показывает карта

- Синий — открытая вода на снимке, не отнесённая к новой воде.
- Красный — вода на месте наблюдаемой суши сравнительной летней базы.
- Зелёный — наблюдаемая суша.
- Серый — неизвестно: облака, тени, снег/лёд, пропуски или неподтверждённый водный класс SCL.

В легенде «новая вода» означает изменение относительно базы. Это кандидат
на затопление, а не подтверждение его причины: сезонные изменения, изменение
русла и ошибки классификации тоже возможны. Вода без надёжной базы остаётся
синей, а её площадь показана отдельно. Серый участок не считается сухим.

В интерфейсе есть дата просмотра, точное время съёмки, возраст снимка к выбранной
дате и на сегодня, доля видимой территории, площади воды и новой воды. Отдельно
показаны исходный RGB и летняя база. Кнопки позволяют перейти к архивному
паводку 2024 года или последнему обработанному снимку.

Если между выбранными датами не было новой обработанной съёмки, отображается
тот же снимок. Более поздние съёмки и ещё не сгенерированные продукты не
используются. Дата обработки архива тоже раскрыта: это не восстановленный
оперативный выпуск прошлых лет.

Время обработки хранится отдельно от съёмки/генерации. При повторном расчёте
из кэша оно не выдаётся за новую загрузку спутниковых данных. Для первых
сохранённых вырезок точное время скачивания не было записано отдельно и
остаётся неизвестным; новые загрузки записывают его в crop.json.

## Как определяется вода

1. Из XML **данного продукта** читаются `BOA_QUANTIFICATION_VALUE` и
   `BOA_ADD_OFFSET`. Отражательная способность = `(DN + offset) / quantification`.
   Offset нельзя игнорировать или определять только по дате съёмки:
   [описание обработки Copernicus](https://sentiwiki.copernicus.eu/web/s2-processing).
2. По [SCL](https://custom-scripts.sentinel-hub.com/sentinel-2/scene-classification/)
   исключаются облака, тени, снег, неопределённые классы и дефектные пиксели.
   Вокруг них добавляется полоса 40 м. NoData исключается отдельно.
3. Рассчитываются `MNDWI = (green − SWIR) / (green + SWIR)` и
   `NDVI = (NIR − red) / (NIR + red)`.
   Вода: **MNDWI > 0.1, NDVI < 0.3, NIR < 0.15**. Это фиксированное
   экспериментальное правило, не нейросеть, обученная на разметке затоплений.
   MNDWI применяется для выделения открытой воды и изменения её площади:
   [описание NASA](https://science.data.nasa.gov/disasters/data-gallery/sentinel-2-mndwi).
4. В v1.1 пиксель SCL=6 («вода»), который правило не подтвердило, становится
   неизвестным. Это защищает от вывода «суша» при несогласии методов.
5. База — три разных дня предыдущего июня–августа в том же тайле. Нужны минимум
   два пригодных наблюдения пикселя: доля воды ≤1/3 — суша, ≥2/3 — вода, иначе
   неизвестно. База не использует ни будущую съёмку, ни более позднюю переработку.
6. Площади считаются по пикселям по 400 м². Неизвестные участки не достраиваются
   и результат не распространяется на весь город.

Правило и его пороги зафиксированы в [протоколе](FLOOD_M2_PLAN.md).
После осмотра ноябрьских сцен добавлено воздержание v1.1; пороги воды не
менялись. Это изменение контроля качества раскрыто в протоколе.

## Какие данные уже получены

Сохранены по четыре сцены на наблюдение: текущая и три базовые. Для каждого
участка есть исторический пример 2024 года и обработанное наблюдение из
интервала 27.10–10.11.2026. Выбирается сцена с минимальной облачностью целого
тайла; она не обязательно самая новая. Локальная пригодность проверяется
уже внутри вырезки. В будущем такой отбор стоит сравнить с отбором по
локальной видимости: малая облачность тайла не гарантирует хорошую вырезку.

В архивных примерах 2024 года новая вода относительно базы:

| Участок | Дата | Видно после контроля качества | Новая вода в вырезке |
| --- | --- | ---: | ---: |
| Якутск | 23.05.2024 | 75% | 9.03 км² |
| Ишим | 24.04.2024 | 81% | 31.45 км² |
| Курган | 20.04.2024 | 69% | 26.82 км² |
| Оренбург | 19.04.2024 | 68% | 8.08 км² |
| Орск | 11.04.2024 | 65% | 28.10 км² |

Это результаты алгоритма, **не независимо подтверждённая площадь затопления**.
В ноябрьском Якутске пригодно меньше 1% вырезки, в Ишиме около 4%: по этим
сценам нельзя судить об отсутствии воды. В Кургане/Оренбурге/Орске осенью
низкое согласие спектрального правила с SCL; интерфейс предупреждает о
возможных пропусках воды даже при высокой доле пригодной территории.

Полные значения, в том числе отрицательные диагностические результаты:
[отчёт](../reports/flood_m2_checks.md), [CSV](../reports/flood_m2_checks.csv).

## Проверка и практические ограничения

Все исходные DN-вырезки после приведения к сетке, STAC и XML сохранены в
`data/flood/satellite/<point>/scenes/`. Результаты — в `runs/`: маска, RGB,
летняя база, геопривязанный PNG и манифест с SHA-256. Временные SAS-токены
в файлы и логи не записываются. Маски и площади пересчитаны из сохранённых
каналов и совпали с результатами. Используется одна точность float64 при
переводе DN в отражательную способность, чтобы пограничные пиксели не
различались между построением и проверкой.

IoU с водным классом SCL — только диагностика согласия: обе маски происходят
из одного снимка. Он рассчитывается до воздержания v1.1, чтобы не скрывать
несогласие. Независимой разметки затопления пока нет; точность в процентах
не заявляется. Мокрый грунт, мутная вода, растительность, облака и снег
могут приводить к ошибкам.

М2 не измеряет глубину и высоту дороги, не различает автоматически мост и
затопленное полотно, не разрешает проезд и пока не корректирует М1. Прежде
чем связывать М2 с планировщиком, нужна отдельная проверка по независимым
контурам затопления и подтверждённым ограничениям дорог.

## Обновление и воспроизведение

Для обновления нужны `requirements-data.txt`. Дашборд читает готовые слои
и не требует rasterio/pyproj для обычного просмотра.

```powershell
python -m pip install -r requirements-data.txt
python scripts/download_flood_m2.py                 # архивные примеры 2024
python scripts/download_flood_m2.py --recent --days 14
python scripts/validate_flood_m2.py
python -m unittest discover -s tests -p 'test_flood*.py'
```

Полностью без сетевых запросов, по сохранённым сценам:

```powershell
python scripts/download_flood_m2.py --rebuild
python scripts/validate_flood_m2.py
```

В существующий workflow ежедневного обновления добавлен шаг Sentinel-2.
Ошибка каталога не подменяет результат нулями. Расписание GitHub Actions
работает в ветке по умолчанию репозитория; наличие workflow в `lambda`
само по себе не включает отдельный ежедневный запуск этой ветки.
